# 逐条批准、结束确认后延迟同步

## 收录范围

收录 AI 专业术语解释，以及学习 AI 时遇到的模型、工具、协议、接口等相关技术名称解释。2026-11-10 用户明确增设“跨专业知识”分类，允许非 AI 领域的概念及区别解释，例如普票与专票的区别；该分类同样逐条确认，不代表自动批准其他条目。条目以“是什么、全称、含义、与相近名称的区别”为核心，不收录个人工作过程、操作教程、部署任务、培训问卷、出图技巧、排错或价格额度查询。出现某个 AI 名称不代表整段工作问答符合范围。

## 两个独立确认

- 发布确认：先展示具体条目的标题和解释摘要，再问“这条笔记是否推送到 GitHub 和网站？”。每条单独记录允许、拒绝或待确认，未回答默认不发布。
- 结束确认：另问“这次是否结束提问？”。结束不等于允许发布；允许一条也不等于允许其他笔记。不把含糊的“好的”同时解释成两个批准。
- 只有先取得具体条目的发布批准，再取得明确结束确认，才安排本批次的延迟同步。没有获准笔记且没有另行获准的站点改动时，不创建空同步任务。
- 结束后才补充批准时，重新确认是否结束，再从新的结束确认计算等待时间。解释内容实质变更后重新取得该条批准。

## 触发流程

1. 在“提问”项目或本笔记站的协作会话中完成用户本次问题。
2. 对符合范围的术语及跨专业知识解释逐条询问是否推送；再独立询问“这次是否结束提问？”。工作问题直接不收录，不生成待推送笔记。
3. 具体条目已获准且用户明确确认结束后，以结束确认消息的时间为起点，安排一个 30 分钟后执行的一次性任务，向用户说明具体时间（Asia/Shanghai）。
4. 使用实际可用的定时工具创建成功后，记录任务 ID、确认时间、消息及内容范围；不得仅凭本说明宣称已经有任务在后台执行。
5. 到时重新核实每条发布授权仍然有效且已等待满 30 分钟，只对获准条目脱敏、测试、构建、提交和推送；检查 GitHub Pages 的部署结果后报告。

## 等待期间继续提问

用户继续提问或撤销确认时，取消或使该次同步任务失效。答复新问题后重新询问是否结束。此前的确认不授权发布新提问，只有重新确认后才重新计算 30 分钟。

## 安全边界

- 不使用每日固定时刻或周期轮询安排发布；旧的每日 9:00 任务已停用。
- 未同时取得条目批准和结束确认时，不自动提交、push 或部署，不为了刷新页面说明而提前发布。
- 未批准和拒绝的内容只保存在被 Git 忽略的 `.sync/drafts/`；不要把草稿混入可推送目录。用户明确批准后才移入 `content/notes.json` 并标记 `publishDecision: "approved"`。已公开的保留条目不伪造新的批准记录。
- “跨专业知识”复用 `term-explanation` 或 `name-explanation` 条目类型，以 `category: "跨专业知识"` 分类；构建必须同时检查明确批准和非空批准依据。通用草稿导入不因新增分类而自动收录非 AI 问答，仍需人工核对。
- 一次性定时能力不可用或创建失败时，说明阻塞，不编造成功，不替换成重复任务。
- 只处理确认范围内的问答和已授权站点改动；保留其他未提交工作，不执行强推，不公开原始聊天或内部资料。
- 先核对每条批准依据、内容和敏感信息，再运行 `node --test tests/*.test.mjs` 及 `node scripts/build.mjs`。提交时明确指定本批次文件，不使用无差别 `git add .`。
- 本地定时任务需要对应机器和应用能运行；无法保证关机时照常执行。补跑时仍需核对确认是否已被撤销。
- 后台同步不是新一轮用户提问，不递归询问或自动安排下一次同步。

本说明和项目指令负责保存工作规则，不是常驻监听器或已经创建的定时任务。每次结束确认对应一个独立任务，以调度工具实际返回成功为准。
